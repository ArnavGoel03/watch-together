# Safari and the App Store: the whole process

**This document is a handoff.** It assumes you have never seen this repository. Read it
top to bottom before touching anything; it is ordered the way the work happens, and every
step says what is already done, what it costs, and what it cannot be undone from.

Written 2026-08-23, against Xcode 26.6 and Safari 27.0 on macOS 27.0.

Two other files you must read before making decisions: `docs/STATE.md` is the state of the
whole project and why every architectural choice is what it is, and `CLAUDE.md` at the
repository root carries the invariants and the traps. This file does not repeat them.

---

## 0. What this is

Watch Together is a browser extension that keeps video playback in step between people
watching the same thing in different browsers, plus a relay it talks to and a marketing
site. It is live on the Chrome Web Store with 37 users, 1.2.2 is in review at both Chrome
and Microsoft Edge as of 2026-08-23, and HEAD is 1.2.3.

Safari is the third browser. It is built and it does not ship, for one reason: Safari
distribution requires the Apple Developer Program at ninety nine dollars a year, and that
has not been bought.

## 1. The state of it, precisely

Split into what was actually verified and what was not, because the difference is the
whole risk.

**Verified on 2026-08-23:**

- `safari/Watch Together/Watch Together.xcodeproj` exists and opens.
- The macOS scheme builds clean in Release.
- The iOS scheme builds clean in Release against `generic/platform=iOS Simulator`.
- The built app is ad-hoc signed and its identifier is `dev.arnavgoel.watchtogether`.
- The extension inside it registers with the system: `pluginkit -a` on the appex reports
  `dev.arnavgoel.watchtogether.Extension`, at whatever version HEAD carries.
- The bundle's `manifest.json` is manifest v3, background `service_worker`,
  permissions `storage`, `tabs`, `scripting`. Contents match the Chrome zip exactly, with
  no Firefox files leaking in.

**Audited on 2026-08-23**, both the extension against Safari's API behaviour and the
generated container app against what would actually reach Apple. Everything the audits
found that could be fixed without running Safari has been fixed and is in 1.2.3: see the
CHANGELOG. Two findings survive as open questions, both in section 6.

**NOT verified, and do not claim otherwise:**

- **Nobody has run it inside Safari.** Not once, by anyone. Building is not running.
- No room has ever been synced with a Safari participant.
- The per-site permission flow on Safari is unexercised and is expected to differ. See
  section 5.

The Firefox build sat packaged and never executed for months, and that is recorded in
`docs/STATE.md` as a mistake. Do not let Safari become the second instance of it.

## 2. How it is wired, and why it matters

Safari does not install a zip. A Safari web extension ships inside a native app, so
`safari/` is an Xcode project generated by Apple's own converter.

**The important property: the Xcode project REFERENCES `extension/` rather than copying
it.** Every path in `project.pbxproj` is relative, of the form
`../../../extension/config.js`. There is one extension source directory, and it feeds
Chrome, Firefox and Safari. A content-script change reaches all three with no copy step
for anybody to forget.

That is deliberate and it is the thing to preserve. If you ever find yourself copying
files into `safari/`, stop: you have just created a second source of truth, and this
repository's first invariant is that there is never a second one.

| | |
| --- | --- |
| Project | `safari/Watch Together/Watch Together.xcodeproj` |
| App bundle id | `dev.arnavgoel.watchtogether` |
| Extension bundle id | `dev.arnavgoel.watchtogether.Extension` |
| Schemes | `Watch Together (macOS)`, `Watch Together (iOS)` |
| Targets | an app and an extension target for each platform |
| Manifest | `extension/manifest.json`, the manifest v3 one Chrome and Edge get |
| Version | HEAD is 1.2.3, in eight build configurations, gated (section 11). 1.2.2 is what is in review at Chrome and Edge |

## 3. Run it locally in two minutes, no Xcode, no account

This is Apple's own fastest path and it is what you should do first, before any build.
It loads the extension folder straight into Safari.

1. Safari, Settings, **Advanced**, tick **Show features for web developers**.
2. Safari, Settings, **Developer**, tick **Allow unsigned extensions**.
   **This resets every time Safari quits.** Set it again on each launch. That is Apple's
   design, not a fault in this build.
3. Safari, Settings, **Developer**, click **Add Temporary Extension...**
4. Choose the `extension/` folder at the root of this repository.
5. Safari switches to the Extensions tab and lists it under Temporary. Enable it and grant
   it access to a site.

Safari removes temporary extensions after 24 hours or when you quit Safari. That is fine
for a first look and useless for anything longer, which is what section 4 is for.

---

## 4. Run it as the real app

```
npm run safari:build      # Release, ad-hoc signed, into safari/build
npm run safari:register   # tells macOS the extension exists, without stealing focus
```

Opening the built app once does the same thing as `safari:register`, and is what an actual
user does. The app is at
`safari/build/Build/Products/Release/Watch Together.app`.

Then enable it: Safari, Settings, Extensions, tick **Watch Together**. "Allow unsigned
extensions" from section 3 still has to be on, because ad-hoc is not a developer identity.

From inside Xcode the equivalent is Product > Run with the macOS scheme selected. To pick
up later changes to `extension/`, Product > Build is enough; Xcode re-embeds the extension
and Safari sees the update.

## 5. The test that actually decides whether this works

Enabling it proves nothing. The product is two people in a room, so test two participants.

**On one Mac you have three ways to get two participants.** Two tabs in one browser is NOT
one of them: one profile runs one background worker, so it holds one connection and one
identity, and a second tab joining from the same profile replaces the first rather than
joining it. That is not a bug and it will look exactly like one.

1. **Two Safari profiles.** Safari 17 and later manage extensions per profile: Settings,
   Profiles, select a profile, Extensions. Enable it in both, then create a room in one
   and join from the other.
2. **Safari and Chrome.** The room lives on the relay, not in the browser, so a Safari
   participant and a Chrome participant belong in the same room. This is also the best
   test there is, because it proves cross-browser sync rather than Safari talking to
   itself.
3. **Safari and Safari Technology Preview**, which is a separate application with separate
   storage.

**What to check, in order:**

1. The toolbar button appears and the popup opens.
2. Creating a room returns a six character code.
3. Joining from the second participant lands both in the same room, both listed by name.
4. Play, pause and seek in either propagate to the other within about a second.
5. The in-page panel opens (bottom right, or the overlay hotkey, Alt and W by default),
   lists both members, and text chat delivers.
6. The member list shows watching, buffering or ad break per person.
7. **The one below.**

## 6. The one place Safari is expected to differ

**Per-site permissions.** The manifest asks for seven video hosts at install and declares
`<all_urls>` as OPTIONAL. Anything else is reached through **Enable on this site** in the
popup, which calls `chrome.permissions.request()`. On Chrome and Edge that produces the
browser's own confirmation dialog and a permanent grant.

Safari does not work that way. It manages site access itself, through Settings,
Extensions, with its own Ask / Allow for One Day / Allow Always model, and its
`permissions.request()` behaviour has never matched Chrome's.

So one of three things is true, and the point of the test is to find out which:

- It works as-is. Do nothing.
- It silently does nothing. The button then needs to become an instruction pointing at
  Safari's own control, and that instruction is **copy, which you do not write**. Propose
  the wording and let the owner decide. See section 13.
- It throws. Then it needs a Safari branch.

Where the code is: the button is `#btnEnableSite` in `extension/popup/popup.html`, wired
in `extension/popup/popup.js`. The grant handler is the `site-granted` path in
`extension/background.js`, which injects into the current tab and then calls
`chrome.scripting.registerContentScripts` so the grant survives future visits.

The rest of the API surface is uncontroversial on Safari 16.4 and later: `storage`,
`runtime`, `tabs`, and the whole `scripting` family including `registerContentScripts`.
The full surface this extension uses is `storage.local`, `runtime.{connect,onConnect,
onStartup,onInstalled,lastError}`, `tabs.{query,get,onRemoved}`,
`scripting.{executeScript,registerContentScripts,getRegisteredContentScripts,
unregisterContentScripts,updateContentScripts}` and
`permissions.{request,getAll,contains,onAdded,onRemoved}`.

### Still open after the audit

**The macOS Extension target has no outgoing-network entitlement while the App target
does.** There are no `.entitlements` files; these are Xcode's synthesized build settings,
and `ENABLE_OUTGOING_NETWORK_CONNECTIONS = YES` is set on the App and not on the
Extension. This is probably harmless: `SafariWebExtensionHandler.swift` does no
networking, and `background.js` runs its WebSocket inside Safari's own WebExtension
process rather than inside this appex. It is left alone deliberately, because this
repository does not widen a permission on a guess. **If the first real run shows rooms
never syncing on Safari with no error anywhere, this is the first thing to try**: add
`ENABLE_OUTGOING_NETWORK_CONNECTIONS = YES` to both Extension configurations.

**The App Store icon is a macOS-shaped icon in an iOS-shaped slot.** Every other icon in
the set has transparent corners, which is right for macOS, where the app supplies its own
shape. `universal-icon-1024@1x.png` is the same artwork flattened onto white, and it is
what iOS and the App Store use, where the icon must be a full-bleed square that Apple
masks itself. The result is a purple rounded tile with a white margin around it, masked
again. It is not broken and it will not fail validation. It is an artwork decision, and
artwork in this project is derived from a master rather than drawn, so it belongs to the
owner and to `scripts/make-icons.py`, not to whoever is reading this.

## 7. Join the Apple Developer Program

Only after section 5 passes. Ninety nine dollars a year, covering macOS, iOS, iPadOS,
visionOS, watchOS and tvOS together.

- Enrol at <https://developer.apple.com/programs/enroll/>.
- Individual enrolment needs a government photo ID, verified through the Apple Developer
  app. A sole proprietorship enrols as an individual by Apple's rule, not by choice.
- Budget roughly a week from starting to being able to submit. It is not instant.
- **The account you enrol with is effectively permanent.** Never an `@icloud.com` address:
  that one is a one-way door. Use a neutral personal address that will still exist in ten
  years, not one on a brand domain that might lapse.

`/stores` in Atlas (<https://atlas.goelhome.workers.dev/stores>) holds the full comparison
of what each store demands, including the parts of Apple enrolment that have no undo.

## 8. Signing, and the identifiers that are permanent

Once enrolled, in Xcode: select each of the four targets, Signing and Capabilities, tick
Automatically manage signing, and choose the team. Replace the ad-hoc signing that
`npm run safari:build` uses; that script exists for the no-account case and stays useful
for local iteration.

**Permanent from the first upload, in exactly the way a Chrome item id is:**

- `dev.arnavgoel.watchtogether` for the app.
- `dev.arnavgoel.watchtogether.Extension` for the extension.

They are reverse DNS from a domain that is actually owned, which is the right shape. They
are free to change today and impossible to change later. **If the product is ever going to
be renamed, rename it before the first submission, not after.** This is recorded as a
standing rule for every store, not just Apple's.

Register the identifiers in the developer portal under Certificates, Identifiers and
Profiles, then create the app record in App Store Connect against the app identifier.

## 9. The App Store Connect listing

A separate listing from Chrome's and Edge's, with its own assets and its own review.

What it wants that the other two do not:

- **An app icon at 1024x1024**, no alpha, no rounded corners. Derive it, do not draw it:
  `python3 scripts/make-icons.py` builds every icon size from one master, and
  `docs/STATE.md` explains why artwork in this project is always derived.
- **Screenshots at Apple's macOS sizes**, which are not the 1280x800 the other two stores
  take. Existing captures live in `~/Desktop/Watch Together store assets/`.
- **Privacy answers**, App Store Connect's own questionnaire. They must agree with
  `/privacy` on the site and with what was told to Chrome and Edge, which is: display
  name, chat, the address of the one attached tab, and playback activity. Not location,
  not website content. The reasoning for each is in `store-listing.md` under Data usage,
  and both other stores were answered from it.
- **Description, keywords, support URL, privacy URL, marketing URL.** The description is
  in `store-listing.md` and is pasted verbatim. Do not write a new one. Support is
  `https://watch.arnavgoel.dev/support`, privacy is `https://watch.arnavgoel.dev/privacy`.
- **A category and an age rating.** Chrome and Edge are both set to Entertainment.

If both macOS and iOS ship, consider Universal Purchase so they are one product rather
than two.

## 10. Archive, upload, submit

1. In Xcode, select the macOS scheme and a real destination, then Product > Archive.
2. In the Organizer, Distribute App, choose **App Store Connect**.
3. Upload, then submit for review from App Store Connect.

For beta testing before that: on macOS use the **Copy App** distribution method, which
produces an unsigned app, and tell testers to enable unsigned extensions exactly as in
section 3. On iOS use TestFlight, or an ad-hoc signed build for registered devices.

There is a second route for macOS only, which does not involve the App Store at all: sign
with a Developer ID and notarize, and distribute the app from your own site. It still
requires the ninety nine dollar membership. It is worth knowing about and it is not the
plan.

## 11. The release gate, which now includes Safari

`npm test` runs lint, six typecheck projects, the dash check, release metadata, and the
node, vitest and worker suites. `npm run test:browser` is separate and loads the extension
in two real Chrome profiles.

Two things in that gate exist because of Safari, and both were put there after the
converter got them wrong:

- **`scripts/check-version.mjs` reads `MARKETING_VERSION` out of the pbxproj** and fails
  the build if it disagrees with `package.json` and the two manifests. The converter seeds
  it at `1.0` in all eight build configurations while the extension says 1.2.2, which
  would ship an app whose version contradicts the extension inside it. The check was
  calibrated with a deliberate mismatch rather than trusted.
- **`scripts/check-dashes.mjs` skips `build` and `xcuserdata`.** Xcode's module cache is
  binary and its bytes contain the same sequence an em dash does. It still catches a real
  dash in authored text; that was verified, not assumed.

ESLint ignores `safari/` because it is a generated Apple template. The extension code it
wraps is linted where it actually lives, in `extension/`.

**Every release bumps the version in four places**: `package.json`, both manifests, and the
pbxproj. The gate refuses anything else, and it also refuses a version with no CHANGELOG
entry.

## 12. Regenerating the Xcode project

Only if the manifest changes shape. The converter overwrites, so everything done by hand
comes back out:

```
xcrun safari-web-extension-converter extension \
  --project-location safari --app-name "Watch Together" \
  --bundle-identifier dev.arnavgoel.watchtogether \
  --swift --no-open --no-prompt --force
```

Then redo both of these, or the gate will catch the second and a reviewer may catch the
first:

1. **Remove the Firefox-only files from the targets.** The converter pulls in everything
   in `extension/`, so `manifest.firefox.json` and `background-firefox.js` ride into a
   submitted Apple binary. A second manifest inside a shipped app is exactly what a
   reviewer notices. Delete their `PBXFileReference` entries, the `PBXBuildFile` entries
   pointing at them, and their lines in the group and the resources build phase.
2. **Set `MARKETING_VERSION`** in all eight configurations to the version in the manifest.

## 13. What is not yours to decide

This repository has hard rules that a new agent will otherwise break in the first hour.

- **Never write user-facing copy.** Nothing a visitor or a store browser can read is yours
  to invent: no descriptions, no button labels, no empty-state text, no alt text. Reuse a
  string that already exists in the project, verbatim. If nothing fits, leave the slot
  empty and propose the wording in chat. `store-listing.md` holds the store text and it is
  pasted, never rewritten. Code comments, commit messages and documents like this one are
  yours to write.
- **No em dashes or en dashes anywhere.** Enforced by the gate.
- **Do not spend the ninety nine dollars, and do not submit anything.** Both are the
  owner's calls.
- **Do not rename the product or change a bundle identifier** without being asked. They
  are permanent after the first submission.
- **37 people are on the live version.** A bug shipped here is a bug in somebody's film
  night, and a store release takes days to review, so it cannot be quietly fixed
  afterwards. Verify before claiming done.
