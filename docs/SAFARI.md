# Safari: built, buildable, not submitted

Written 2026-08-23. The Safari app exists, both platforms compile, and nothing about it
is waiting on code. It is waiting on ninety nine dollars a year.

## What it is

Safari does not install a zip. A Safari web extension ships inside a native app, so
`safari/` holds an Xcode project generated by Apple's own converter, and that project
**references `extension/` rather than copying it**. Every path in the project file is
relative (`../../../extension/config.js` and so on), which is the whole point: one
extension directory feeds Chrome, Firefox and Safari, and a change to a content script
reaches all three without a copy step that somebody forgets.

| | |
| --- | --- |
| Project | `safari/Watch Together/Watch Together.xcodeproj` |
| App bundle id | `dev.arnavgoel.watchtogether` |
| Extension bundle id | `dev.arnavgoel.watchtogether.Extension` |
| Targets | Watch Together (macOS), Watch Together (iOS), and an extension target for each |
| Manifest | the manifest v3 one, the same file Chrome and Edge get |
| Version | 1.2.2, in eight build configurations, enforced by `npm run check:dashes`'s neighbour `scripts/check-version.mjs` |

Both targets build clean today: macOS against `platform=macOS`, iOS against
`generic/platform=iOS Simulator`.

## Build and run it locally, no account required

```
npm run safari:build      # ad-hoc signed, into safari/build
npm run safari:register    # tells macOS the extension exists
```

Then, once, in Safari:

1. Safari, Settings, Advanced, tick **Show features for web developers**.
2. Develop menu, **Allow Unsigned Extensions**. An ad-hoc signature is not a developer
   signature, and without this Safari refuses to list the extension. It resets every time
   Safari restarts, which is Apple's design and not a bug in this build.
3. Safari, Settings, Extensions, enable **Watch Together**, and give it access to a site.

Opening the built app once also registers it, which is what a normal user does. The
`safari:register` script does the same thing without stealing focus.

## The one thing most likely to need Safari-specific work

**Per-site permission granting.** The extension asks for seven video hosts at install and
declares `<all_urls>` as OPTIONAL, so anything else is reached through "Enable on this
site" in the popup, which calls `chrome.permissions.request()`. Chrome and Edge answer
that with their own confirmation dialog and the grant is permanent.

Safari does not work that way. It manages site access itself, through Settings,
Extensions, with its own Ask / Allow for One Day / Allow Always choices, and its
`permissions.request()` behaviour has never matched Chrome's. So the button may do
nothing useful on Safari, or may need replacing with an instruction pointing at Safari's
own control.

**This has not been tested by a human yet**, and it is the first thing to check when it
is. The rest of the API surface is uncontroversial on Safari 16.4 and later: `storage`,
`runtime`, `tabs`, and the whole `scripting` family including
`registerContentScripts`.

## What is actually left before it can ship

1. **The Apple Developer Program, ninety nine dollars a year.** Nothing else on this list
   can start without it. It covers macOS, iOS and every other Apple platform.
2. **Run it in Safari and use it**, both sides of a room, before deciding it works. The
   Firefox build spent months packaged and never once executed; do not repeat that here.
3. **Decide the bundle identifier before the first submission.** `dev.arnavgoel.watchtogether`
   is reverse DNS from a domain that is actually owned, which is the right shape, but it
   is permanent from the first upload in exactly the way a Chrome item id is. It is free
   to change today and impossible to change later.
4. **App Store Connect listing.** Separate from the Chrome and Edge listings, with its own
   screenshots at Apple's sizes, its own privacy answers, and an app review that judges
   the wrapper app as an app, not just the extension inside it.
5. **Decide whether iOS ships at all.** The target builds, but an in-page overlay driving
   video on iOS Safari is a different product question from the desktop one, and the
   streaming services people watch on iOS are mostly native apps rather than Safari.

## Regenerating the project

Only if the manifest gains something structural. The converter overwrites, so anything
done by hand comes back out:

```
xcrun safari-web-extension-converter extension \
  --project-location safari --app-name "Watch Together" \
  --bundle-identifier dev.arnavgoel.watchtogether \
  --swift --no-open --no-prompt --force
```

Two things must then be redone, and both are why this section exists:

- **Delete the Firefox-only files from the target.** The converter pulls in everything in
  `extension/`, so `manifest.firefox.json` and `background-firefox.js` ride along into a
  submitted Apple binary. They are removed from the project file; a regeneration puts
  them back.
- **Set `MARKETING_VERSION`.** The converter seeds every one of the eight build
  configurations at `1.0` rather than reading the manifest, which would ship an app
  called 1.0 wrapping an extension called 1.2.2. `scripts/check-version.mjs` fails the
  build if that happens, so this cannot silently escape again.
